## 1. pipeline.cpp — 构造函数 Config Dump (L73-99)

**问题**: 27 行 spdlog::info，逐条打印所有配置参数。典型的"AI想表现自己很全面"输出。

```
spdlog::info("[pipeline] OdometryPipeline created");
spdlog::info("[pipeline]   scan_voxel_size={}m", ...);
spdlog::info("[pipeline]   crop_box: [{:.2f},{:.2f},{:.2f}] → ...");
spdlog::info("[pipeline]   submap: distance={}m, rotation={}rad, ...");
spdlog::info("[pipeline]   observer: Kp={} Kv={} Kq={} Kab={} Kgb={}");
spdlog::info("[pipeline]   registration: {}", ...);
spdlog::info("[pipeline]   cuda: {}", ...);
spdlog::info("[pipeline]   imu_init: gyro_std<{:.4f}, ...");
```

**为什么是废话**: 这些参数已经写在 TOML 配置文件里，用户改配置时就知道。运行时打印出来纯粹是终端噪音。尤其是 `cuda: ON/OFF` 这个字段 —— 代码里 cuda.enabled=true 就直接 throw，根本不可能出现 ON。

**建议**: 删到只剩 1-2 行关键信息，或者改成 `spdlog::debug`。

```cpp
spdlog::info("[pipeline] ready: registration={}, deskew={}, submap_kf={}",
    config.registration.type,
    config.deskew.time_offset ? "offset" : "zero-ref",
    config.odometry.submap.max_keyframes);
```

## 2. sapphire_ros.cpp — 构造函数 Topic Dump (L109-124)

**问题**: 16 行 RCLCPP_INFO，打印所有订阅/发布 topic。

```
RCLCPP_INFO(this->get_logger(), "Sapphire ROS2 wrapper ready");
RCLCPP_INFO(this->get_logger(), "  Subscribed: lidar/points, imu/data");
RCLCPP_INFO(this->get_logger(), "  Publishing: sapphire/odometry, ...");

RCLCPP_INFO(this->get_logger(), "  IMU acceleration scale: %.6f", acc_scale_);
```

**为什么是废话**: ROS2 launch 文件和 rqt_graph 已经能告诉你全部 topic 信息。`acc_scale_` 本身就是个 ROS2 parameter，`ros2 param list` 就能看。

```cpp
RCLCPP_INFO(this->get_logger(), "[sapphire_ros2] ready");
```

## 3. types.hpp — OdometryDiagnostics 含纯打印字段

**问题**: 以下 3 个字段存在于 `OdometryDiagnostics` 里，从 deskew → commitLidarOutputs → diagnostics 一路搬运，最终以 diagnostic_msgs 发布。它们不是为了算法决策，纯粹是为了"可视化性能"。更关键的是，它们让诊断消息膨胀到 30+ 个 key-value 对。

```
size_t deskew_timestamp_groups = 0;   // pipeline.cpp:473
size_t deskew_imu_intervals = 0;      // pipeline.cpp:475
size_t deskew_pim_copies = 0;         // pipeline.cpp:477
```

**为什么是废话**: 
- `timestamp_groups` = 点云去重后的时间戳数量，纯实现细节
- `imu_intervals` = IMU积分区间数，等于 IMU 样本数 - 1
- `pim_copies` = PIM 对象拷贝次数，纯性能调试用

这三个值对用户没有任何意义。放在 `DeskewMetrics` 内部结构里自己统计就行，不需要暴露到诊断输出。

**建议**: 从 `OdometryDiagnostics` 删除这三个字段，以及 `commitLidarOutputs` 里对应的赋值行（L472-478），和 `sapphire_ros.cpp` `publish_diagnostics` 里对应的 `diagnosticValue` 调用（L372-378）。

## 4. pipeline.cpp — commitLidarOutputs 纯搬运函数 (L451-503)

**问题**: 52 行函数，做的事就是把各个子模块的输出字段复制到一个 `latest_result_.diagnostics` 结构体里。没有逻辑，没有判断，没有转换 —— 纯粹是 struct → struct 字段搬运。

```
// 16 行 deskew metrics
latest_result_.diagnostics.deskew_timeline_ms    = deskewed.metrics.timeline_ms;
latest_result_.diagnostics.deskew_integration_ms  = deskewed.metrics.integration_ms;
latest_result_.diagnostics.deskew_transform_ms    = deskewed.metrics.transform_ms;
latest_result_.diagnostics.deskew_total_ms        = deskewed.metrics.total_ms;
latest_result_.diagnostics.deskew_timestamp_groups = deskewed.metrics.timestamp_groups;
latest_result_.diagnostics.deskew_imu_intervals    = deskewed.metrics.imu_intervals;
latest_result_.diagnostics.deskew_pim_copies       = deskewed.metrics.pim_copies;

// 6 行 registration results
latest_result_.diagnostics.registration_ms   = artifacts.result.elapsed_ms;
latest_result_.diagnostics.fitness_score     = artifacts.result.fitness_score;
latest_result_.diagnostics.num_inliers       = artifacts.result.num_inliers;
latest_result_.diagnostics.iterations        = artifacts.result.iterations;
latest_result_.diagnostics.source_points     = artifacts.source_points;
latest_result_.diagnostics.target_points     = artifacts.target_points;

// 5 行 submap stats
latest_result_.diagnostics.keyframe_count          = submap_manager_.keyframeCount();
latest_result_.diagnostics.stored_keyframe_points  = submap_manager_.storedPointCount();
latest_result_.diagnostics.registration_accepted   = artifacts.result.accepted;

// 2 行 bias
latest_result_.diagnostics.accel_bias = observer_update.accel_bias;
latest_result_.diagnostics.gyro_bias  = observer_update.gyro_bias;
```

**为什么是废话**: 如果下游真的需要这些诊断数据，应该让下游自己去取（submap 有自己的 public API，registration 有 result 结构体）。把这些全部压扁到一个巨大的 diagnostics 结构体里，然后又在 `sapphire_ros.cpp` 里逐个拆出来转成 ROS diagnostic_msgs，是经典的 "AI 过度工程"。

**建议**: 要么让 commitLidarOutputs 只搬运真正对外的 3-4 个关键指标（preprocess_ms、registration_ms、fitness、accepted），要么考虑用 OdometryDiagnostics 包含子结构体引用而不是拷贝。

## 5. deskew.hpp — DeskewResult::converged 永远是 true

**问题**: `deskew.cpp:373` 和 `deskew.cpp:43`:

```cpp
result.converged = true;   // line 373 — always set when Success
```

```cpp
struct DeskewResult {
    ...
    bool converged = false;  // line 43 — default false
};
```

**为什么是摆设**: deskew 这个操作不存在"收敛"的概念。它要么成功返回 Success，要么失败返回 EmptyScan/NoPointTimestamps/...（此时走 makeFallback，converged 保持默认 false）。这个字段从来没有被任何代码读取过 —— pipeline.cpp 里检查的是 `deskewed.status != DeskewStatus::Success`，不检查 converged。

**来源判断**: AI 生成的代码习惯性地给所有 Result 结构体加 `converged` 字段，因为它在生成 "RegistrationResult" → "OdometryResult" → "DeskewResult" 时复制了相同的模式。

**建议**: 删除 `DeskewResult::converged` 字段。

## 6. 中等问题

### 6.1 submap target 重建日志重复 (pipeline.cpp:373-378, 527-532, 403-407)

```
// initializeFirstLidarTarget() 里:
spdlog::info("[pipeline] submap target rebuilt: keyframes={}, points={}, revision={}", ...);
spdlog::info("[pipeline] first LiDAR target initialized: stamp={:.6f}, points={}", ...);

// maybeUpdateSubmapTarget() 里:
spdlog::info("[pipeline] submap target rebuilt: keyframes={}, points={}, revision={}", ...);
```

第一帧时会连续输出两条 info（重建 + 初始化），正常帧每 N 帧输出一条重建。建议：submap 重建改成 `spdlog::debug`，只在第一帧保留 info。

### 6.2 latestPropagatedResult() 死字段 (pipeline.cpp:149)

```
result.converged = true;  // 永远不会是 false（因为前面已经 return nullopt 了）
```

如果函数返回了一个值，`converged` 必然是 true。下游 `sapphire_ros.cpp:271` 检查的是 `result.converged`（来自 latestResult），这个字段有其他代码路径设 false（registration 被拒绝时），所以 latestResult 的 converged 是有意义的。但 `latestPropagatedResult` 的 converged 是摆设。

### 6.3 voxel_filter.cpp:54 — 绕弯路的常数

```cpp
const double coordinate_limit = std::ldexp(1.0, 63);
```

`std::ldexp(1.0, 63)` = 2^63 = 9.22e18。目的是防止 int64 溢出。但这个写法需要读者心算 ldexp 的含义。建议：

```cpp
constexpr double kInt64MaxAsDouble = 9223372036854775808.0;  // 2^63
```

### 6.4 Diagnostic 消息膨胀 (sapphire_ros.cpp:356-411)

`publish_diagnostics` 函数发布了 30 个 key-value 对。`diagnostic_msgs/DiagnosticArray` 不是用来做性能面板的。`rqt_runtime_monitor` 显示这些会严重卡顿。

建议：只保留 5-6 个运维级别的指标（registration_accepted, fitness_score, num_inliers, registration_ms, keyframe_count, pgo_loop_edges），其余删掉。

### 6.5 过度注释 (多处)

AI 写的代码习惯给每个小函数写 3-4 行 doxygen 风格注释，哪怕函数只有 5 行。例如：

- `registration.cpp:56-58` — "DLIO pattern: both clouds already contain the IMU world-frame prior..." 三行注释解释为什么不需要 guess。函数里根本没传 guess，不需要解释为什么不传。
- `deskew.hpp:46-53` — Doxygen 风格参数文档，但每个参数都已经有自解释的名字。

这些注释不删也行，但它们增加了代码的 "AI味"。
