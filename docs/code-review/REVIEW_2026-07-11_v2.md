## 2. PGO Backend — Detailed Review

### 2.1 Architecture

```
PoseGraphBackend (public API, PIMPL)
  └── Impl
        ├── input_frames_[]   ← addFrame() from frontend (mutex)
        ├── frames_[]         ← copyPendingFrames() transforms odom→lidar frame
        ├── worker_ thread    ← 1Hz timer: buildOdometryGraph → ISAM2 → buildLoopEdges → ISAM2
        ├── optimized_        ← ISAM2 Values (GTSAM key = frame index)
        ├── T_map_odom_       ← latest map-from-odom correction (mutex)
        └── global_map_       ← lazy-rebuilt on requestGlobalMap()
```

**Design decisions verified correct:**
- ISAM2 keys are frame indices (0, 1, 2, ...), consistent across incremental updates
- `buildOdometryGraph` creates a fresh `NonlinearFactorGraph` per cycle; ISAM2 `update()` efficiently incorporates only new factors
- `T_map_odom` correction bridges map frame (ISAM2 optimized) and odom frame (frontend)
- PIMPL hides GTSAM headers from public API — good compilation isolation
- PCL ICP used for loop registration (see §2.5 for GICP recommendation)

### 2.2 Keyframe Selection

```cpp
// pose_graph.cpp:130-137 (Impl::addFrame)
const Isometry3d delta =
    input_frames_.back().T_odom_lidar.inverse() * T_odom_lidar;
if (delta.translation().norm() < config_.keyframe_distance
    && rotationAngle(delta) < config_.keyframe_rotation) {
    return;  // skip — not enough motion
}
```

Independent from frontend submap policy (SubmapManager). Both operate on odom-frame poses. Correct.

### 2.3 Odometry Graph Construction

```cpp
// pose_graph.cpp:270-308 (Impl::buildOdometryGraph)
if (added_odom_id_ == 0) {
    graph.add(PriorFactor<Pose3>(0, first, prior_noise_));  // anchor
    initial.insert(0, first);
    added_odom_id_ = 1;
}
for (size_t i = added_odom_id_; i < frames_.size(); ++i) {
    graph.add(BetweenFactor<Pose3>(i-1, i, relative, odom_noise_));
    initial.insert(i, estimate_from_last_optimized);
    ++added_odom_id_;
}
```

Initial guess for new frame `i`:
```
estimate = last_optimized * T_odom_lidar[last_optimized_id]⁻¹ * T_odom_lidar[i]
```

This chains the optimized pose through subsequent odometry increments. Correct, but when ISAM2 optimization barely changes poses, the initial guess adds no new information — ISAM2 relinearization may waste computation. Not a bug, but worth documenting the trade-off.

### 2.4 Loop Detection

```cpp
// pose_graph.cpp:310-345 (Impl::searchLoopTarget)
// Candidate must satisfy ALL:
//   1. spatial distance < loop_search_radius (default 15m)
//   2. time separation > loop_min_time_separation (default 30s)
//   3. travel distance > loop_min_travel_distance (default 30m)
//   4. orientation difference < loop_max_rotation (default 3.14 rad = 180°)
//   5. candidate index < query_id (historical only)
//   6. candidate index < optimized_.size() (already ISAM2-optimized)
```

The guard at line 319-320 prevents duplicate reciprocal loop edges:
```cpp
const size_t candidate_count = std::min(query_id, optimized_.size());
```
When multiple frames are copied in one worker cycle, `optimized_` may contain nodes newer than an early query. Without this guard, query 10 could find "loop" with target 11 (both newly optimized), creating a short useless edge.

**[MEDIUM]** See §4.3: `loop_max_rotation = 3.14` is too permissive.

### 2.5 Loop Registration

```cpp
// pose_graph.cpp:362-389 (Impl::registerLoop)
pcl::IterativeClosestPoint<Point, Point> icp;  // point-to-point ICP
icp.setMaxCorrespondenceDistance(config_.loop_search_radius * 2.0);
icp.setMaximumIterations(50);
icp.align(aligned, initial_pose.matrix().cast<float>());
return icp.hasConverged() && finite && fitness < config_.fitness_threshold;
```

**[HIGH]** PCL point-to-point ICP is suboptimal for loop closure. DLIO and SimpleLoopClosure use PCL GeneralizedICP. Viewpoint changes at loop closure are significant — GICP's covariance-weighted correspondences are more robust.

**Recommendation:** Replace with `small_gicp::RegistrationPCL<Point, Point>`. Already a dependency — zero additional cost. Set `setNumThreads(4)` for parallelization.

The `max_correspondence_distance = loop_search_radius * 2.0` (default 30m) is aggressive but justified: accumulated odometry drift can be large. The `fitness_threshold` (default 0.5) filters bad registrations.

### 2.6 Build Target Cloud

```cpp
// pose_graph.cpp:347-360 (Impl::buildTargetCloud)
// Merges target_frame_count frames on each side of the candidate
// → VoxelGrid downsample → return
```

With `target_frame_count = 50`, this merges 101 frames. The voxel downsample (0.4m default) keeps the point count manageable, but the merge itself is O(frames * points_per_frame). Acceptable for 1Hz backend worker.

**[MEDIUM]** See §4.4: missing bounds check on `frames_[i]` access.

### 2.7 Worker Thread Lifecycle

```cpp
// pose_graph.cpp:205-223 (Impl::workerLoop)
// 1Hz sleep → processPending() → repeat
// stop_ atomic flag checked on wake + after unblock
~Impl() {
    stop_.store(true, memory_order_release);
    wake_cv_.notify_all();
    if (worker_.joinable()) worker_.join();
}
```

Correct: `notify_all()` ensures the worker wakes from `wait_for` even during sleep. `join()` blocks until the worker exits cleanly.

### 2.8 Thread Safety

| Data | Protected by | Access pattern |
|------|-------------|----------------|
| `input_frames_` | `input_mutex_` | Frontend writes, worker reads |
| `T_map_odom_`, `stats_`, `global_map_`, snapshots | `output_mutex_` | Worker writes, frontend reads |
| `frames_`, `optimized_`, ISAM2 state | (worker thread only) | Single-threaded by design |
| `stop_`, `map_requested_` | `std::atomic` | Lock-free |

No data races. The frontend (`addFrame`) and read paths (`T_map_odom()`, `stats()`, `snapshot()`) can run concurrently with the worker.

## 3. Pipeline Integration

### 3.1 PGO Correction Application

```cpp
// pipeline.cpp:102-108
OdometryResult latestResult() const {
    OdometryResult result;
    { std::lock_guard lock(output_mutex_); result = latest_result_; }
    return applyGlobalCorrection(result, pgo_backend_.T_map_odom());
    //     ↑ called outside output_mutex_ — PgoBackend has its own mutex
}
```

No data race (PgoBackend uses internal `output_mutex_`). But there's a frame-level temporal mismatch: `result` may be from scan N while `T_map_odom` is from scan N±1. At 10Hz LiDAR / 1Hz PGO, worst case is ~1 frame off. Impact: negligible since PGO corrections are smooth.

**[LOW]** Document this temporal semantics.

## 4. Issues Found

### 4.1 [HIGH] Per-scan spdlog::info flooding

**Files:** `pipeline.cpp:239-252` (deskew), `registration.cpp:58-61` (GICP)

Both log at `spdlog::info` level every scan (10Hz = 20 lines/sec). Violates the project logging convention (first 5 frames + every 20 frames throttled). Buries real diagnostic output.

**Fix:** Change both to `spdlog::debug`, or add the existing throttle counter pattern.

### 4.2 [HIGH] PCL ICP for loop registration → should be small_gicp GICP

**File:** `pose_graph.cpp:369`

See §2.5. PCL point-to-point ICP is inferior to GICP for loop closure with viewpoint changes.

**Fix:** Replace with `small_gicp::RegistrationPCL<Point, Point>`. One-time setup in constructor, reuse per-call.

### 4.3 [MEDIUM] `loop_max_rotation` default 3.14 rad (180°)

**File:** `types.hpp:213`

```cpp
double loop_max_rotation = 3.14;  // effectively disables orientation check
```

A loop candidate with 180° yaw difference passing the check can produce wrong constraints. DLIO uses ~0.5 rad (30°) as default.

**Fix:** Change default to 0.5, or explain why 180° is intentional (e.g., handling revisits from opposite direction in structured environments).

### 4.4 [MEDIUM] Missing bounds check in buildTargetCloud

**File:** `pose_graph.cpp:347-358`

```cpp
for (int i = begin; i <= end; ++i) {
    const Isometry3d pose = fromGtsam(optimized_.at<gtsam::Pose3>(i));
    *merged += *transformedCloud(frames_[i].cloud_lidar, pose);
    //                                ^^^^^^^^  no bounds check
}
```

`target_id` from `searchLoopTarget` is guaranteed < `optimized_.size()` (by `candidate_count`), but `begin..end` range may extend beyond `frames_.size()` if ISAM2 ever has more Values than frames (edge case: could theoretically happen if ISAM2 keeps marginalized keys in Values).

**Current safety:** ISAM2 does not delete Values, and `buildOdometryGraph` keeps `optimized_.size() == added_odom_id_ <= frames_.size()`. So safe, but fragile.

**Fix:** Add `assert(end < static_cast<int>(frames_.size()))` or runtime guard.

### 4.5 [MEDIUM] Observer orientation correction uses linear approximation

**File:** `observer.cpp:57-61`

```cpp
Eigen::Quaterniond q_correction(
    1.0 - std::abs(q_error.w()),  // linear approximation of 1-cos(θ)
    q_error.x(), q_error.y(), q_error.z());
```

DLIO's original uses `so3_exp(Kq*dt*so3_log(q_error))` which exactly preserves the rotation group structure. The linear version is accurate for small errors (GICP gives ~cm-level, so rotation error is tiny), but a GICP outlier that passes rejection could produce a non-unit quaternion before normalize().

**Fix:** Align with DLIO's exponential map for correctness in edge cases.

## 8. Architecture Notes

### 8.1 Strengths

- **Clean frontend/backend separation:** PGO runs on its own thread, frontend never blocks on ISAM2 optimization
- **PIMPL hides GTSAM:** Public header is 73 lines, zero GTSAM exposure
- **Subscriber-driven visualization:** Only rebuilds global map when RViz is actually subscribed
- **Good use of atomics:** `stop_`, `map_requested_` are lock-free
- **Config validation comprehensive:** `validateConfig()` checks all PGO parameters

### 8.2 Potential Future Refactors

- `Impl` class is ~500 lines — could split into `LoopDetector`, `GraphBuilder`, `MapRebuilder` components
- Loop detection is purely spatial (distance-based). Adding ScanContext or similar appearance-based detector would reduce false negatives in visually distinct but spatially close environments
- PGO worker fixed at 1Hz — could benefit from adaptive rate (faster when new frames arrive, slower when idle)

### 8.3 Novelty Impact on PGO

The PGO backend is a standard ISAM2 + spatial loop detection design (similar to LIO-SAM, DLIO). This does not dilute Sapphire's novelty claim — the novelty is in the **frontend** (Gal(3) equivariant preintegration for deskew + propagation), not the backend. The backend's job is to correct accumulated drift, and ISAM2 is the established tool for that.
