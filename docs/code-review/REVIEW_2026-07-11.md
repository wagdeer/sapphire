## Executive Summary

Sapphire core (663 lines of C++) is solid early-stage code with a clean architectural boundary between core and ROS wrapper. The Gal(3) deskew is theoretically correct and well-tested. No critical correctness bugs were found in the current code path. However, there are 2 high-severity issues, 4 medium-severity issues, and several design-level concerns that should be addressed before registration integration.

**Bottom line: safe to proceed with registration integration, but fix the high-severity items first.**

## 1. CRITICAL BUGS (produces wrong results or crashes)

### 1.1 [HIGH] `integrateMeasurement` parameter order confusion — VERIFIED CORRECT

**File:** `deskew.cpp:195-207`  
**Status:** ✅ VERIFIED CORRECT — naming is misleading but logic is right

The `EquivariantPreintegration::integrateMeasurement` signature is:
```cpp
void integrateMeasurement(const Vec3 &accMeas, const Vec3 &gyroMeas, const FPType dt)
```

Internally it constructs `Input u(gyroMeas, accMeas)` — swapping the parameters. This means the function's first parameter (named `accMeas`) is actually passed as the gyro input, and the second (`gyroMeas`) as the accel input.

Sapphire calls: `integrateMeasurement(measurement.accel, measurement.gyro, partial_dt)` → `Input u(gyro=accel, accel=gyro)`? NO — `Input u(gyroMeas=gyro, accMeas=accel)`. Result: gyro goes where gyro should go, accel goes where accel should go. **CORRECT.**

However, the misleading parameter names are a future maintenance trap. A developer who reads only the function signature will swap them.

**Recommendation:** Add a static assertion test or rename the parameters in the vendored header.

### 1.2 [HIGH] `assert()` used for runtime guards in 3 places — Release-mode UB

**Files affected:**
- `pipeline.cpp:53` — `assert(imu_init_result_.has_value())` in `correctImu()`
- `pipeline.cpp:88` — `assert(imu_state_.valid)` in `deskewPointcloud()`
- `imuInitResult()` accessor — `return *imu_init_result_` (no guard at all)

**Impact:** In Release builds (`-DNDEBUG`), these assertions disappear. If code flow somehow reaches `correctImu()` before init, it dereferences an empty `std::optional` → undefined behavior (likely segfault).

**The callers do guard correctly** (pushLidar checks `initialized_`, pushImu checks `!initialized_`). However, defensive programming in a safety-critical system demands runtime checks, not asserts.

**Fix:**
```cpp
// Instead of:
assert(imu_init_result_.has_value());

// Use:
if (!imu_init_result_.has_value()) {
    spdlog::error("[pipeline] correctImu called before IMU init — BUG");
    return raw;  // return uncorrected as fallback
}
```

Similarly for `imuInitResult()`:
```cpp
const ImuInitializer::Result& imuInitResult() const {
    if (!imu_init_result_.has_value()) {
        throw std::logic_error("imuInitResult accessed before initialization");
    }
    return *imu_init_result_;
}
```

## 2. IMPORTANT ISSUES (correctness risks, semantic errors)

### 2.1 [MEDIUM] TOML config loaded but never used at runtime

**Files:** `config.cpp`, `sapphire_ros.cpp:16-17`

`SapphireRos` constructor creates `sapphire::Config config;` — using **hardcoded C++ defaults**. The `loadConfig()` function is implemented and tested, but **never called in production**:

```cpp
// sapphire_ros.cpp:16-17
sapphire::Config config;  // ← hardcoded defaults only
pipeline_ = std::make_unique<sapphire::OdometryPipeline>(config);
```

**Impact:** Users cannot adjust GICP parameters, crop box, IMU noise, or extrinsics without recompiling. The entire TOML parsing infrastructure is dead code at runtime.

**Fix:** Load from a config file path (CLI argument or ROS param):
```cpp
sapphire::Config config = sapphire::loadConfig("/path/to/sapphire_mid360.toml");
```

### 2.2 [MEDIUM] `publish_deskewed()` uses wrong frame_id

**File:** `sapphire_ros.cpp:204`

```cpp
ros_msg.header.frame_id = "lidar";
```

The deskewed point cloud is in **world frame** (odom), not LiDAR frame. RViz will display it at the wrong location if the tf tree is set up correctly.

**Fix:**
```cpp
ros_msg.header.frame_id = "odom";
```

This matches DLIO's convention where `deskewed_pub` publishes in the odom frame.

### 2.3 [MEDIUM] RingBuffer: `physicalIndex` logic correct but unguarded

**File:** `ring_buffer.hpp:97-101`

```cpp
size_type physicalIndex(size_type logical) const {
    if (size_ < N) return logical;  // buffer not yet wrapped
    return (head_ + logical) % N;
}
```

**Analysis:** When `size_ < N`, `head_` equals `size_` (number of elements pushed). The valid logical indices are `[0, size_-1]`. `physicalIndex(0)` = 0 → first element, correct. When full, `head_` points to the oldest element → `physicalIndex(0)` = `head_` → oldest, correct.

**Issue:** No bounds checking. `operator[](size()+1)` reads garbage from the unused portion of the array. This is expected for performance, but inconsistent with the Iterator which uses `end() = size_`.

**Recommendation:** Document as "caller must ensure index < size()" and consider `assert(i < size_)` in debug mode.

---

### 2.4 [MEDIUM] Deskew fallback: `v_world_ref` uses wrong velocity source

**File:** `deskew.cpp:62`

```cpp
result.v_world_ref = v_world;
```

In `makeFallback()`, the returned velocity is the *previous* velocity `v_world_prev`, not the velocity at the scan's reference timestamp. DLIO's fallback also propagates velocity. This means if the robot is accelerating during a fallback frame, the velocity in the result is stale.

**Impact:** Minor — fallback frames are already degraded. But if registration later uses `v_world_ref` for IMU propagation, the error accumulates.

**Recommendation:** Propagate velocity through the time interval even in fallback, or mark `v_world_ref` as invalid.

## 4. ALGORITHM CORRECTNESS (deep dive)

### 4.1 Gal(3) Deskew: Sapphire vs DLIO

| Aspect | DLIO | Sapphire |
|--------|------|----------|
| Integration | Single pim, continuous | Single pim + partial copies |
| Recovery | slerp interpolation | Full Gal3: Gamma * Xi * Upsilon |
| Output frame | World (odom) | World (odom) |
| Speed state | slerp ignores velocity | ✅ Preserves v via Gal3 |

**Sapphire's approach is theoretically superior.** Full Gal3 recovery preserves the velocity state, which matters for the IMU propagation baseline. DLIO's slerp only recovers rotation + translation, discarding the velocity component of the Gal(3) state.

However, the partial copy approach (line 192: `Pim partial = pim;`) has a **performance cost**: each unique timestamp within an IMU interval creates a full copy of the 20×20 covariance matrix. For a Mid-360 scan with ~100 unique timestamps, this is ~100 × 400 doubles × 8 bytes = 320KB of stack allocation per scan. Acceptable for 10Hz, but worth noting.

### 4.2 ImuInitializer: MAD filter correctness

**File:** `imu_init.cpp:108-111`

```cpp
auto mad = [](std::vector<double>& v, double median) {
    for (auto& x : v) x = std::abs(x - median);
    return computeMedian(v) / kMADScale;
};
```

This destructively computes absolute deviations in-place (overwrites the channel vectors). The channel vectors are local copies (`gyro_x`, etc.) created at line 83-90, so the original `samples_` vector is not modified. **Correct.**

The MAD threshold of 5.0 is standard for robust statistics. The scale factor 0.6745 (= Φ⁻¹(3/4)) converts MAD to a consistent estimator of σ for normally distributed data. **Correct.**

### 4.3 ImuInitializer: Overlapping MAD + mean computation

**File:** `imu_init.cpp:141-185` (`checkConvergence`) and `:187-275` (`computeResult`)

Both `checkConvergence()` and `computeResult()` call `rejectOutliers()` independently. This means outliers are filtered TWICE:
1. First in `checkConvergence()` (line 142) — modifies `samples_` by removing outliers
2. Then in `computeResult()` (line 188) — runs MAD again on already-filtered data

The double-filtering is **not harmful** (already-filtered data won't have outliers for the second pass), but it's redundant. The second `rejectOutliers()` at line 188 copies all 6 channels, computes medians again, and finds no new outliers. This adds ~O(N) work unnecessarily.

**Recommendation:** Skip the second `rejectOutliers()` in `computeResult()`, or refactor to compute statistics once.

### 4.4 Gravity alignment detail: accel_bias sign

**File:** `imu_init.cpp:216-226`

```cpp
Eigen::Vector3d grav_imu = accel_mean.normalized();
Eigen::Vector3d grav_world(0.0, 0.0, 1.0);
Eigen::Quaterniond q_gravity = Eigen::Quaterniond::FromTwoVectors(grav_imu, grav_world);

Eigen::Vector3d grav_in_imu = q_gravity.inverse() * Eigen::Vector3d(0, 0, cfg_.gravity_mag);
Eigen::Vector3d accel_bias = accel_mean - grav_in_imu;
```

At rest, the IMU measures the support force ≈ +g upward. `q_gravity` maps IMU-frame vectors to world-frame (Z-up). `q_gravity.inverse()` maps world to IMU. `(0,0,+g)` in world is the upward direction. In the IMU frame, this is what the IMU would measure if there were zero bias. Subtracting this from the actual measurement gives the bias. **Correct.**

The test `pipeline_test.cpp:81` verifies this: `accel_bias.isZero(1e-9)` for pure gravity input.

### 4.5 Registration: T_correction semantics

**File:** `registration.cpp:88-89`

```cpp
result.T_correction  = T_correction;
result.T_world_lidar = T_correction;  // caller composes with prior
```

The comment says "caller composes with prior." When registration is integrated into the pipeline, the caller must do:
```cpp
latest_result_.T_world_lidar = reg_result.T_correction * latest_result_.T_world_lidar;
```

This is documented in the skill doc's registration pitfalls section. The current pipeline doesn't call registration yet, so this is not yet testable.

**Note:** DLIO's `getFinalTransformation()` returns T_s2t (source-to-target). When both clouds are in the world frame (deskew output), the GICP result IS the correction between scans. This is consistent with both DLIO and Sapphire conventions.

## 7. DLIO COMPARISON — Key Differences

| Feature | DLIO | Sapphire | Assessment |
|---------|------|----------|------------|
| IMU init | Simple 3s fixed window | Variance-driven MAD convergence | Sapphire better |
| Deskew method | slerp interpolation | Full Gal3 recovery | Sapphire better |
| Output velocity | slerp ignores velocity | Preserved via Gal3 | Sapphire better |
| Thread pool | BS::light_thread_pool | None (v0.1 single-threaded) | Planned |
| Geo Observer | Yes (online bias est.) | No (v0.1 only static init) | Planned |
| Voxel downsampling | Yes (0.05m) | No (planned) | Planned |
| Submap | OctVoxMap + k-NN | Not implemented | Planned |
| Degeneracy detection | SVD soft-threshold | Not implemented | Future |
| Adaptive params | Spaciousness + density | Not implemented | Future |
| IMU transform | Baslink2imu extrinsic | Not handled (assumes co-located) | v0.1 simplification |
| Accel scale/misalign | SM matrix | Not handled | v0.1 simplification |

### 7.1 DLIO deskew: Key difference in `integrateImu`

DLIO's integrateImu (line 1495-1579 of odom.cc) uses a **single continuous pim** and slerp interpolation within IMU intervals. Sapphire's approach uses **partial pim copies** with exact Gal3 recovery. Both are correct, but:

- DLIO: faster (no copy), less accurate (slerp ignores velocity)
- Sapphire: more accurate (full Gal3), more CPU (copies)

For Mid-360 at 10Hz, Sapphire's approach is fine. For 100Hz LiDARs, consider DLIO's approach.
